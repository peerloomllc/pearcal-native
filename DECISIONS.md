## 2026-04-28 — desktop ships on Electron, not the Pear runtime
Tier: T2
Context: Phases 1–3 of the original `2026-04-27-pear-desktop.md` plan targeted Pear runtime, the same stack mobile uses for the bare worklet. Phase 2.4 hit a wall: `bare-pack` output (`desktop/bare-desktop.bundle`, ~66 MB) cannot be loaded into Pear's bare worker. The `.bundle` extension handler triggers a JSON walk-up that resolves to binary content from Pear's own corestore. Two alternative load paths (`Pear.worker.run('./bare-desktop.bundle')` directly; a `worker/` subproject with `pear: { type: "terminal" }`) both fail. Renderer-side workarounds also accumulated: Pear has no native window chrome, no `shell.openExternal`, no native-addon loading over `pear://`, and no auto-update model that fits our distribution. Mobile stays on Pear-runtime-equivalent paths via BareKit; desktop has no analogous host.
Choice: Pivot desktop to plain Electron + electron-builder, mirroring PearGuard Windows. A 33-line BareKit shim (`electron/src/main/barekit-shim.js`) installs `global.BareKit = { IPC: ... }` so the unmodified `src/bare.js` runs in Electron's Node main process. Native binaries (sodium-native, et al.) are handled by the standard prebuilt + `electron-rebuild` paths — no cross-runtime translation. Packaging is `electron-builder` with platform-native conventions: `.dmg` (Mac, signed + notarized + stapled via SSH to Mac Mini), unsigned NSIS `.exe` (Windows, built on a libvirt KVM Win11 VM shared with PearGuard at `ben@192.168.50.157`), `.AppImage` + `.deb` (Linux, built locally). Renderer-side native intercepts (`openURL`, `nativeShare`, `exportIcs`, `exportRecoveryPhrase`, `takePhoto`, `scheduleForEvent`, deep links, tray + close-to-tray) live in `electron/src/main/shell-handlers.js` and follow the same method-name contract mobile uses. `src/bare.js` is shared with mobile unchanged, except for three `bare-fs`/`bare-path` requires gated on `typeof Bare !== 'undefined'` (storageBreakdown, rebuildLocalDb, reclaimStorage) — bare-fs reads `Bare.platform` and calls `require.addon` at module load, both unavailable under Node.
Alternatives considered: (a) keep pushing Pear runtime — fixing the bundle-load resolution would require either upstream Pear changes or shipping bare.js as inline source the Pear renderer evaluates, both fragile. (b) Tauri (Rust + system webview) — would force a second bare.js IPC translation layer and gives up Electron's sodium-native prebuild story. (c) Native Cocoa/Win32/GTK with bare bundled separately — far more code, three platforms diverge, no shared maintainer. (d) Flutter desktop — same translation cost as Tauri, plus a third UI tree to maintain. Electron loses on bundle size (~150 MB per platform) but wins on every other axis: shared codebase with mobile, mature signing/packaging, BareKit shim is trivial, the same primary-developer can ship all three platforms.
Consequences: Mac signing pipeline now runs against the existing `pearcal-notary` notarytool keychain profile and `Developer ID Application: G79ALD29NA` cert (Phase 0 from the original plan) — no new Apple Developer cost. Windows ships unsigned in v1, matching PearGuard; SmartScreen friction is real but acceptable for a private/dogfood release. Wired via `feature/pear-desktop` branch; commits `0d87e00` (Mac sign+notarize), `9cf6b71` (icon + multi-size Linux hicolor), `36692e9` (Windows pipeline + bug fixes), `3f583fd` + `174256b` (tray icon). `desktop/` (the Pear-runtime version) lives in git history at `c926826` for reference; not maintained in parallel. Plan doc: `docs/superpowers/plans/2026-04-27-pear-desktop-electron-pivot.md`. E5 (hardening + parity QA) and E6 (desktop UI redesign) are queued.

## 2026-04-27 — personalSeenGroup marker gates cleanupStalePersonalGroups
Tier: T2
Context: `cleanupStalePersonalGroups` (added in `cc9046d` to prevent ghost auto-joins after a kicked sibling left state behind) deletes a `personalGroups:{id}` view entry when no matching local `groups:{id}` exists. The 2026-04-26 multi-device audit identified a race: on a freshly-paired secondary, personal-base `personalGroups:` ops arrive ahead of the group autobases (independent swarm topics, independent replication speed). The naive "no local group" check would sweep every entry on first boot, replicate `del` ops to siblings, and orphan the entire identity from every group.
Choice: stamp `personalSeenGroup:{groupId}` in local DB inside the personal-base apply branch — placed AFTER the local group record is seeded, so marker-present implies group-was-seeded-locally. Cleanup deletes only when EITHER `blockedFromGroup:{id}` (explicit kick) OR (`personalSeenGroup:{id}` is set AND `groups:{id}` is missing). Fresh secondaries with no markers are immune by construction; the sweep no-ops on first boot, then runs normally once mirror has caught up.
Alternatives considered: (a) skip the sweep entirely if it would delete >0 entries — heuristic, brittle under partial replication. (b) defer cleanup behind a fixed timer — heuristic, wrong on slow networks. (c) gate cleanup on an Autobase-internal "has-replayed-everything" signal — no clean upstream API; would need to poll `base.update()` and synthesize a stable point. The marker is a clear local invariant tied to apply ordering, idempotent, and survives reboots.
Consequences: one new local-only persisted key class, never replicated. Old peers ignore it; mixed installs are safe. The marker stays after voluntary leave or kick — harmless, since the cleanup matches on `(marker AND no local group)` so a re-joined group naturally re-seeds the local record and re-stamps the marker. Cleanup is now genuinely safe on freshly-paired secondaries; this is unrelated to the still-hidden `Sweep Orphaned Data` button (`f63dc23`) which is a separate `auditStorage` / `purgeOrphanDataRanges` issue with its own root cause.

## 2026-04-26 — deviceMeta apply skips view.put; row seeded lazily on user rename
Tier: T2
Context: TODO #95 v1 added a `deviceMeta:{writerKey}` keyspace to the personal Autobase for the linked-devices list. Initial implementation seeded each device's row on boot inside `ensurePersonalBase` and put new rows into both the linearized view and local DB. Integration testing on TCL surfaced a recurring `HypercoreError: INVALID_OPERATION: Truncation breaks prologue` from Autobase `_drain` → `ApplyState.undo` → `view.core.truncate`, killing the bare runtime ~7s after open. After much chasing this turned out to be corrupt state in a separate test group's Autobase, not the personal base — recreating the group cleared the crash. But two of the workarounds tried during the chase were kept because they're harmless and reduce blast radius for similar bugs.
Choice: (a) `deviceMeta` apply branch writes only to local DB (`db.put`), not to the linearized view (`view.put`). (b) The local writer's row is appended lazily — first append happens when the user calls `setDeviceNickname`; until then `listLinkedDevices` injects a synthetic placeholder so the UI always shows "This device".
Alternatives considered: keep `view.put` for parity with other apply branches; keep boot-seed for symmetry with `seedIdentityProfileIfNeeded`. Both rejected as net-zero benefit given the tiny data footprint and the soft margin against future Autobase drain weirdness.
Consequences: cross-device sync still converges via apply-on-every-peer; freshly-paired devices learn existing `deviceMeta` rows via writer-hypercore replay (no view fast-path). Other apply branches (event/reminders/note/identityProfile/groupMembership) keep the standard `view.put` pattern. Followup TODO to revisit if and when the Autobase truncate-vs-prologue bug has an upstream fix.
