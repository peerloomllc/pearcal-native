## 2026-08-28 - the seeder heals a copied data folder instead of staying down
Tier: T1 (TODO #172). Local storage logic only, no wire change, no Hyperbee key change.
Context: hypercore-storage opens every store through `device-file`, whose CORESTORE marker records the file's own inode and a created stamp and refuses to open ("Invalid device file, was modified") when either changes. The guard exists so two live copies of a core never both write. StartOS 0.4.0.1's first boot clones each package volume into a btrfs subvolume and deletes the original, so every file gets a new inode and birth time while exactly one copy remains. Both seeders on the Start9 crash-looped from 16:08 on 2026-08-28 until the three markers were rewritten by hand.
Choice: `src/lib/deviceFileHeal.js` re-stamps a marker in place (same file, same inode, extended attribute untouched) and `init` in `src/seed.js` retries the open once after healing. Only the exact "was modified" error is healed. "was moved unsafely" (attribute missing, what rsync without -X or a cross-filesystem copy produces) and "different platform" still fail, because those are the copies the guard is really for. `PEARCAL_SEED_NO_DEVICE_HEAL=1` turns it off.
Alternatives considered: (a) leave the guard alone and document the manual repair - rejected, every Start9 seeder user hits it on the OS update with no UI hint. (b) a "Repair storage" action in the Start9 package - still worth having, but it needs the user to know what happened. (c) heal every DEVICE_FILE error - rejected, that removes the protection entirely.
Consequences: the seeder is blind and never writes a member's cores, only its own local Hyperbee, so the worst case of a wrongly healed marker is a forked seeder-state bee, which nothing else reads. The member app (`src/bare.js`) is NOT changed: it does write, and a copied phone data folder is exactly what the guard must catch there. Same change belongs in PearCircle's seeder.

## 2026-07-23 - PearCal adopts the suite's blind relay as a direct-first fallback, plus an off switch
Tier: T2 (TODO #130). The T3 that built this transport and stood up the infrastructure was PearTune's, under `../peartune/proposals/2026-07-23-blind-relay.md`; PearCal consumes an already-approved, already-deployed, deliberately app-agnostic service and adds no infrastructure of its own, which is what keeps this a tier below.
Context: Hyperswarm hole-punches directly or not at all. On a symmetric / double-randomized NAT the punch aborts with `HOLEPUNCH_ABORTED` after ~10s and no retry budget rescues it - PearTune measured 12% per attempt on a Pixel over Google Fi, and a genuinely symmetric user sits at ~0%. PearCal is the worst case in the suite for this: it is phone-TO-phone, so both ends are routinely on carrier CGNAT at once, where PearTune's hard case was only phone-to-host. The existing blind seeder covers async DATA sync for groups that have one, but it does not help live peer connectivity, pairing, or reaching the seeder itself from off-LAN.
Choice: pass `relayThrough` to the one `new Hyperswarm(...)` in `src/bare.js`, pointed at the same PeerLoom relay key PearTune deployed (`qshao3eawtzecrt5p7buswr4meyyhw6q6b51qtxazd8wwfdp8uqy`). The policy is a pure function in `src/lib/relay.js` (`relayThroughFor`) and is passed as a FUNCTION rather than a static key, so it is evaluated per dial: null on the normal attempt, the relay key only once Hyperswarm has set `force=true` after a hole-punch abort for that peer. Hyperswarm's own `shouldForceRelaying` already implements exactly that escalation, so there is no second connection path and no raw `dht.connect` fallback. A device-local `deviceSetting:useRelay` toggle (default on, surfaced as Profile → Connection) gates it ahead of every other condition, held in memory because `relayThrough` is called on every connect and cannot await a DB read - so flipping it applies to the next dial with no reconnect. The key is stored twice, hex for decoding (so this module adds no dependency `bare.js` did not already have) and z32 for display, with a unit test asserting the two agree.
Alternatives considered: (a) do nothing and lean on the blind seeder - rejected, it is per-group opt-in hardware and does nothing for pairing or live sync. (b) set `relayThrough` on the accepting side too - actively harmful: hyperdht's server relays whenever `relayThrough || remotePayload.relayThrough` is set, so it would burn a relay dial on connections that punched fine. Verified against the source that the requesting side alone is sufficient; a stock peer sustains a relayed connection it never configured. (c) default the toggle OFF - rejected: a user who cannot connect at all has no way to know a relay would fix it, so the failure would present as "the app is broken" and the setting would never be found.
Consequences: no wire change, no protocol change, no key material anywhere near the relay - the stream stays Noise-encrypted end to end and the relay carries ciphertext plus metadata (which two keys talk, how much). It is transient encrypted transit, not storage, and the README now says exactly that rather than implying zero-knowledge. Rollback is one constant: empty `RELAY_PUBLIC_KEY_HEX` and the policy returns null everywhere, which is byte-for-byte today's behaviour; a dead relay degrades the same way. The relay is a shared single point and an open forwarder by construction (PearTune's stated v1 abuse posture: caps plus stat visibility, per-key allow-list as the named next step) - PearCal inherits that risk rather than adding to it. Not yet done: the phase-3 hardware gate, i.e. observing an actual relayed connect on a genuinely-0%-punch network. Desktop (Electron) picks this up for free from the shared `src/bare.js`; the blind seeder deliberately does not, since the phone requesting is sufficient to relay a phone-to-seeder connection.

## 2026-07-23 - keyless members recover via a fresh invite, not a key over the wire
Tier: T2
Context: A plain member that loses a group's `encryptionKey` can never self-heal. `backfillMissingGroupEncryptionKeys` restores a key from the personal-base `personalGroups:` fan-out, which exists ONLY for paired sibling devices of the same identity, so a member of someone else's group has nothing to restore from. Reproduced 2026-07-23 with the headless two-peer harness: the device shows every symptom at once, `members=1` (only itself), the owner's events never arrive, the owner never sees it at all, and its record would mint invites with no `&enc=`, breaking whoever accepts them. Two findings reshaped the option set. First, `groupSwarmTopic` derives the encrypted topic as `blake2b('pearcal-enc-topic-v1:' + groupKey)`, from `groupKey` ALONE, so a keyless device CAN compute it and reach keyed peers, and Hypercore block encryption does not prevent ciphertext replication. Every recovery option was therefore technically available, which is not what it looks like from the code. Second, a damaged encrypted group and a legacy unencrypted group are indistinguishable on disk, both being just a record with no `encryptionKey`. That ambiguity, not reachability, was the real obstacle.
Choice: Option (a) from `proposals/2026-07-23-keyless-member-recovery.md`. A monotonic `encrypted` latch rides the existing `putGroupRecord` choke point, set the first time any key is seen and never cleared, so it outlives the key's loss by construction and makes `encrypted && !encryptionKey` a definitive offline answer. A never-synced heuristic (joined over 24h ago, still no peer-supplied membership) covers devices damaged before the latch existed, surfaced as a soft warning because an all-offline group looks identical. A fresh invite carrying `enc=` for an already-held keyless group is routed into `reconcileGroupEncryptionKey` rather than `joinGroup`, which early-returns on `bases.has`; `handleInviteLink` previously answered `already_member` and stopped, which is exactly what made the only cure a dead end. Latch and classifier are pure decisions in `src/lib/groupRecord.js` next to `resolveGroupEncryptionKey`.
Alternatives considered: (b) member-to-member key request over the writer-announce channel, authenticated against `members[].identityPublicKey`. Technically feasible given the topic finding, and it would heal automatically with no user action, but it puts the group's block-encryption key on the wire, making it T3 with its own threat model, rollback and RCA readiness. Rejected. (c) detect and warn only, with no guided recovery. Cheapest and safest, but leaves the user to work out unaided that a fresh invite is the cure, which is the gap that kept this invisible. Also considered and deliberately deferred: probe-joining the derived encrypted topic, which would upgrade the heuristic to a certainty for exactly the devices we cannot otherwise help, but a naive probe reintroduces the EncTestv hazard the topic separation was built to remove (keyless peers triggering owner-recovery on a false "owner offline" reading and emitting member removals over the plaintext control channel).
Consequences: one new local-only persisted field, never appended to a view and therefore never observed by any peer, old or new. No wire change, no invite-format change, no key material on the wire, no migration step, and revert-to-roll-back. The latch self-sets on the next group-record write for any device that still holds its key. Verified end to end on the real worklet over Hyperswarm: keyless member repaired from a fresh invite, key restored, `encrypted` latched, membership went 1 to 2, and a subsequent owner event arrived, so sync was genuinely restored rather than just the record patched. Still open (proposal open question 3): a keyless device continues to mint invites with no `&enc=`, which is how one damaged device becomes several. Not folded in because it changes behaviour for legacy unencrypted groups too, which share the same "no key" state.

## 2026-04-28 — desktop ships on Electron, not the Pear runtime
Tier: T2
Context: Phases 1–3 of the original `2026-04-27-pear-desktop.md` plan targeted Pear runtime, the same stack mobile uses for the bare worklet. Phase 2.4 hit a wall: `bare-pack` output (`desktop/bare-desktop.bundle`, ~66 MB) cannot be loaded into Pear's bare worker. The `.bundle` extension handler triggers a JSON walk-up that resolves to binary content from Pear's own corestore. Two alternative load paths (`Pear.worker.run('./bare-desktop.bundle')` directly; a `worker/` subproject with `pear: { type: "terminal" }`) both fail. Renderer-side workarounds also accumulated: Pear has no native window chrome, no `shell.openExternal`, no native-addon loading over `pear://`, and no auto-update model that fits our distribution. Mobile stays on Pear-runtime-equivalent paths via BareKit; desktop has no analogous host.
Choice: Pivot desktop to plain Electron + electron-builder, mirroring PearGuard Windows. A 33-line BareKit shim (`electron/src/main/barekit-shim.js`) installs `global.BareKit = { IPC: ... }` so the unmodified `src/bare.js` runs in Electron's Node main process. Native binaries (sodium-native, et al.) are handled by the standard prebuilt + `electron-rebuild` paths — no cross-runtime translation. Packaging is `electron-builder` with platform-native conventions: `.dmg` (Mac, signed + notarized + stapled via SSH to Mac Mini), unsigned NSIS `.exe` (Windows, built on a libvirt KVM Win11 VM shared with PearGuard at `ben@192.168.50.157`), `.AppImage` + `.deb` (Linux, built locally). Renderer-side native intercepts (`openURL`, `nativeShare`, `exportIcs`, `exportRecoveryPhrase`, `takePhoto`, `scheduleForEvent`, deep links, tray + close-to-tray) live in `electron/src/main/shell-handlers.js` and follow the same method-name contract mobile uses. `src/bare.js` is shared with mobile unchanged, except for three `bare-fs`/`bare-path` requires gated on `typeof Bare !== 'undefined'` (storageBreakdown, rebuildLocalDb, reclaimStorage) — bare-fs reads `Bare.platform` and calls `require.addon` at module load, both unavailable under Node.
Alternatives considered: (a) keep pushing Pear runtime — fixing the bundle-load resolution would require either upstream Pear changes or shipping bare.js as inline source the Pear renderer evaluates, both fragile. (b) Tauri (Rust + system webview) — would force a second bare.js IPC translation layer and gives up Electron's sodium-native prebuild story. (c) Native Cocoa/Win32/GTK with bare bundled separately — far more code, three platforms diverge, no shared maintainer. (d) Flutter desktop — same translation cost as Tauri, plus a third UI tree to maintain. Electron loses on bundle size (~150 MB per platform) but wins on every other axis: shared codebase with mobile, mature signing/packaging, BareKit shim is trivial, the same primary-developer can ship all three platforms.
Consequences: Mac signing pipeline now runs against the existing `pearcal-notary` notarytool keychain profile and `Developer ID Application: G79ALD29NA` cert (Phase 0 from the original plan) — no new Apple Developer cost. Windows ships unsigned in v1, matching PearGuard; SmartScreen friction is real but acceptable for a private/dogfood release. Wired via `feature/pear-desktop` branch; commits `0d87e00` (Mac sign+notarize), `9cf6b71` (icon + multi-size Linux hicolor), `36692e9` (Windows pipeline + bug fixes), `3f583fd` + `174256b` (tray icon). `desktop/` (the Pear-runtime version) lives in git history at `c926826` for reference; not maintained in parallel. Plan doc: `docs/superpowers/plans/2026-04-27-pear-desktop-electron-pivot.md`. E5 (hardening + parity QA) and E6 (desktop UI redesign) are queued.

## 2026-04-27 — personalSeenGroup marker gates cleanupStalePersonalGroups
Tier: T2
Context: `cleanupStalePersonalGroups` (added in `cc9046d` to prevent ghost auto-joins after a kicked sibling left state behind) deletes a `personalGroups:{id}` view entry when no matching local `groups:{id}` exists. The 2026-04-26 multi-device audit identified a race: on a freshly-paired secondary, personal-base `personalGroups:` ops arrive ahead of the group autobases (independent swarm topics, independent replication speed). The naive "no local group" check would sweep every entry on first boot, replicate `del` ops to siblings, and orphan the entire identity from every group.
Choice: stamp `personalSeenGroup:{groupId}` in local DB inside the personal-base apply branch — placed AFTER the local group record is seeded, so marker-present implies group-was-seeded-locally. Cleanup deletes only when EITHER `blockedFromGroup:{id}` (explicit kick) OR (`personalSeenGroup:{id}` is set AND `groups:{id}` is missing). Fresh secondaries with no markers are immune by construction; the sweep no-ops on first boot, then runs normally once mirror has caught up.
Alternatives considered: (a) skip the sweep entirely if it would delete >0 entries — heuristic, brittle under partial replication. (b) defer cleanup behind a fixed timer — heuristic, wrong on slow networks. (c) gate cleanup on an Autobase-internal "has-replayed-everything" signal — no clean upstream API; would need to poll `base.update()` and synthesize a stable point. The marker is a clear local invariant tied to apply ordering, idempotent, and survives reboots.
Consequences: one new local-only persisted key class, never replicated. Old peers ignore it; mixed installs are safe. The marker stays after voluntary leave or kick — harmless, since the cleanup matches on `(marker AND no local group)` so a re-joined group naturally re-seeds the local record and re-stamps the marker. Cleanup is now genuinely safe on freshly-paired secondaries; this is unrelated to the still-hidden `Sweep Orphaned Data` button (`f63dc23`) which is a separate `auditStorage` / `purgeOrphanDataRanges` issue with its own root cause.

## 2026-04-26 — deviceMeta apply skips view.put; row seeded lazily on user rename
Tier: T2
Context: TODO #95 v1 added a `deviceMeta:{writerKey}` keyspace to the personal Autobase for the linked-devices list. Initial implementation seeded each device's row on boot inside `ensurePersonalBase` and put new rows into both the linearized view and local DB. Integration testing on TCL surfaced a recurring `HypercoreError: INVALID_OPERATION: Truncation breaks prologue` from Autobase `_drain` → `ApplyState.undo` → `view.core.truncate`, killing the bare runtime ~7s after open. After much chasing this turned out to be corrupt state in a separate test group's Autobase, not the personal base — recreating the group cleared the crash. But two of the workarounds tried during the chase were kept because they're harmless and reduce blast radius for similar bugs.
Choice: (a) `deviceMeta` apply branch writes only to local DB (`db.put`), not to the linearized view (`view.put`). (b) The local writer's row is appended lazily — first append happens when the user calls `setDeviceNickname`; until then `listLinkedDevices` injects a synthetic placeholder so the UI always shows "This device".
Alternatives considered: keep `view.put` for parity with other apply branches; keep boot-seed for symmetry with `seedIdentityProfileIfNeeded`. Both rejected as net-zero benefit given the tiny data footprint and the soft margin against future Autobase drain weirdness.
Consequences: cross-device sync still converges via apply-on-every-peer; freshly-paired devices learn existing `deviceMeta` rows via writer-hypercore replay (no view fast-path). Other apply branches (event/reminders/note/identityProfile/groupMembership) keep the standard `view.put` pattern. Followup TODO to revisit if and when the Autobase truncate-vs-prologue bug has an upstream fix.
